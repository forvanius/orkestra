# Roles and operating rules

- **User:** set direction, approve the plan as required by the mode, make design choices and run the real-world test. During Scope ask where and how it will happen for this project (device, server, live data, game feel or none). Record it in the plan. At Close show the board's try-note and turn feedback into new parts.
- **Conductor:** plan, split, route and decide. Recommend Opus for ambiguous or design-heavy jobs and Sonnet 5.5 for well-defined jobs. The user chooses the session model. Never switch it. Keep routine contact to decisions and real-world tests, with updates at agreed checkpoints.
- **Writer:** default to Codex Sol (`codex_model`). Use Sonnet workers only for local debugging or hard multi-file changes. Mechanical low-risk work goes to Haiku or `codex_model_light`.
- **Codex briefs:** include the template's CONSTRAINTS CHECKLIST, with a checked item and evidence for every constraint in the report. Copy RUN ENVIRONMENT from the project's AGENTS.md (interpreter path, browser or engine, cwd and other paths, exact test command). If missing, the conductor adds it to AGENTS.md once before dispatch. A Codex-written test that needs a runtime unavailable in the sandbox must run with the verifier before review.
- **Verifier:** Haiku runs short deterministic checks, imports and commits Codex's work when allowed. If commit permission is refused, the conductor commits. Visual approval belongs to the designer in `visual-check` mode. For a run expected to take >8 minutes or marked LONG, the conductor starts `node "<skill dir>/run_long.js" --log "<job dir>/<part>-run.log" -- <cmd> [args...]` in the background. Preserve the brief's runtime, cwd and heavy-run guard where applicable. Feed the exit and evidence back into verification before review. A verifier never hands back mid-run.
- **Report intake:** Pass an explicit `.txt` filename to `take_report.js` for both collection and fallback. Pipe a refused write's whole final message with `--stdin`. If the shell cannot preserve UTF-8 through stdin, save the whole message as UTF-8 and pass `--file <final-message>` instead.

## Quiet waiting and handoff

- Delegate images, long logs, test output and merge debugging. Read only the verifier's ≤8-line result. Send captures to the user or verifier without opening them.
- Read what a decision rests on (two REVISEs, a `must` you would reject, a finding that changes direction). Record `read: <file> — <why>` under Decisions.
- Each call re-reads context. Bundle shell steps, use `close_part.js`, and let the verifier read diffs and reports. Start parallel Codex runs as **one** background command: `( <guarded command A> ) & a=$!; ( <guarded command B> ) & b=$!; wait "$a"; a_exit=$?; wait "$b"; b_exit=$?; printf 'A=%s B=%s\n' "$a_exit" "$b_exit"; [ "$a_exit" -eq 0 ] && [ "$b_exit" -eq 0 ]`. Redirect each child's output to its own log. Let the batch report only on completion. No Monitor, polling, tailing logs or “still waiting” turns. If no notice has arrived after the expected limit (~25 min by default), check once and stop a stuck run. `audit_run.js --here` reports `idle_wakes` and `repeat_notices`.
- At +250 K context growth (`handoff_guard` warns, then every 50 K), finish the current request and take no new one. At +400 K start no new part or brief and let running parts finish. In either case update the board, fill Next session, leave no part running, and pass `node "<skill dir>/board_check.js" <board.md> --handoff --repo <repo>`. Tell the user to open a new session and say `/orkestra:orkestra continue from <board path>`.

## Review and merge

- Before every code part starts, record BASE. Package with `node "<skill dir>/review_package.js" <job dir> <part> <base> <head> --repo <repo>`. Match the package name to the board part and save the result as `review-<part>.json` next to the board. Use the review template. Route to the other vendor. Leave severity and findings to the reviewer and gate the verdict by script.
- High risk requires both `orkestra:reviewer` and Codex on `high`, same schema, neither sees the other. Save the Claude review as `review-<part>.json` and the Codex review as `review-<part>-codex.json` with package `<part>-codex`. Merge only if both approve and pass `--review` twice. Other code parts need one review.
- On REVISE, send the fix to Codex even when Claude wrote the part. Re-review with Claude (and both vendors for high risk). Pass only open blockers and the fix: name the package `<part>-2` and use the head the previous review saw as BASE. The second high-risk package uses `<part>-2-codex`.
- After two REVISEs in the primary review files, `next_parts.js` surfaces the part in `needs_decision`. Apply the same stop if the second review in a high-risk pair caused a REVISE. The conductor diagnoses and rules in auto. In checkpoints/ask the user decides. For round 3 and beyond, package `<part>-3` (or the actual round suffix) with `--ruling "<what — why — cost if wrong>"` in auto or `--user "<their words>"` in checkpoints/ask. The script refuses without the mode's decision flag and records a supplied decision on the board.
- `close_part.js` gates the review, records evidence, cherry-picks, marks the part merged and confirms it is on HEAD. Exit 1 with REVISE gives the blockers. `UNREVIEWED` means the review missed commits or predates the package, so review again. For `cannot_verify`, make the decision read and add `--checked "<what you checked>"`. Tests-only notes come back as `verifier_runs` for the verifier.
- Exit 3 means the pick was aborted and the part is unmerged. For `cause=conflict`, follow the skill's file-ownership rule and git reference. For `git-identity`, the retry with each commit's author failed and the user must set an identity. For `git`, read the error. Rerun after resolving the cause. Then the verifier runs full QA.
- At cleanup, run `git status` in the repo and every worktree. List the job's leftover untracked tools, captures and scratch files to the user, and remove worktrees you created.

## Budget and quota

Write `## Budget` at Plan with `- Estimate: claude_reads=<N>M conductor=<N>M time=<N>h`. Use numbers, including decimals when needed. At each checkpoint show `usage_sum.js --here --budget <board>` spent vs estimate. For a job of the recent pilots' scale, aim for total Claude reads below about 30 M, conductor reads below about 15 M and no quota stop.

`guarded.js quota` reports a Claude 5-hour read estimate in `claude`. Set `claude_window_reads_m` in plugin options to use a threshold in millions. Empty leaves the estimate informational. On exit 4 inspect `blocked`: route around a Codex limit with eligible Claude work, or around a Claude limit with Codex. Raise a user decision if neither lane can proceed.
